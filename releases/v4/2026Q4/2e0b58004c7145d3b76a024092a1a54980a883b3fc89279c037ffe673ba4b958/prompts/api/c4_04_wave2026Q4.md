# c4_04_wave2026Q4: Reconcile revised payments, disputes and credit

Calls are independent. Do not print results. Use standard libraries/built-ins only. JSON object key order is ignored; arrays, booleans, nulls and numeric values matter. Integers/intermediates are within the exact signed 53-bit range unless the contract specifies strings. Only stated input domains and error cases are tested.

ONE-SHOT: one metered raw API response, no tools or execution.

Output-token scoring budget: 16,000, including reasoning and all model/tool-interaction output. Wall-time scoring budget: 450 seconds, including tool work. The headline discounts positive credit by min(1, token budget / output tokens). TIME-DL separately discounts positive credit by min(1, wall-time budget / measured seconds). Write one SQLite query for the as-of collections report. Tables (all columns
have the declared SQLite INTEGER or TEXT affinity; no implicit NULLs):

config has exactly one row. accounts.id and invoices.id are unique; invoice
account references an account. Each payments (event,revision) pair is unique.
Dispute IDs are unique. There are no other uniqueness assumptions. Payment
revisions may move an event to another invoice. Payments/disputes may reference
unknown or currently ineligible invoices; those references contribute nothing.

For each payment event first choose its greatest revision among known_at<=asof.
Then retain it only if occurred<=asof AND status='settled'; do not fall back to an
older version when the chosen one is pending/void/future. Sum signed retained
amounts per invoice (negative payments are refunds). Eligible invoices have
issued<=asof and (void_at IS NULL or asof<void_at). Only enabled=1 accounts appear.
Gross outstanding=max(0,invoice.amount-signed_payments), with missing sum=0.
An invoice is disputed if ANY interval has start<=asof and
(stop IS NULL or asof<stop). Disputed invoices have collectible=0; others have
collectible=gross. Overlapping disputes must not multiply any amount.

Account credit=max(0,sum signed credits.amount WHERE at<=asof). Allocate credit
only to collectible balances in ascending (due,id) order, consuming as much as
possible at each invoice. Do not allocate the same credit twice to tied due dates.
Residual=collectible minus that invoice's allocation. An invoice is overdue iff
residual>0 AND due<asof-2; the grace boundary is strict. Within the ordered
list of ALL eligible invoices, longest overdue streak counts consecutive overdue
invoices; every non-overdue invoice, including disputed or fully paid, breaks it.

Return rows sorted by account ID, with seven columns:
account_id, eligible_invoice_count, sum_gross_outstanding, sum_residual,
overdue_invoice_count, longest_overdue_streak, earliest_residual_invoice_id_or_NULL.
The last ID uses the same (due,id) order and residual>0, regardless of overdue.
Include enabled accounts with no eligible invoices using zeros and NULL.

Bounds per database: <=500 accounts, 5,000 invoices, 20,000 payment revisions,
10,000 disputes and credits; IDs ASCII <=80 characters; integer magnitudes <=10^8,
all aggregates within signed 53-bit range. amount on invoices is nonnegative;
credits/payments may be signed. All non-NULL interval ends >= starts. Status is
settled/pending/void; enabled is 0 or 1; revision is positive. Group <=34 databases.
