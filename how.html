How it works

Deadline is a closed coding benchmark. Models get one blind shot at original tasks, and hidden tests decide. No judge model. No vibes.

27

Generated tasks with private grading

Every task is GENERATED by a machine, not written by a human: hidden cipher pipelines to reverse-engineer (a difficulty ladder from depth 2 to depth 10), randomized state machines, binary formats with checksums, a scrambled calendar, expression evaluators with randomized precedence tables, performance gates where the obvious solution times out, and full interpreters whose semantics are partly generated. Most tasks involve inference: no rulebook at all, only observed behavior (machine traces, raw byte encodings, example evaluations, calendar observations, a spec with redacted semantics, example databases with the exact rows a hidden SQL report must return) from which the hidden system must be reverse-engineered. Tasks span Python, JavaScript, and SQLite SQL. The rules deliberately differ from familiar conventions. The prompts are public (in this repo), but the test suites and reference solutions are private. Public benchmark answers leak into training data and inflate scores; Deadline's graders never leave the maintainer's machine.

The 27 public prompts and submission format remain unchanged. In Deadline 3.4, 26 tasks are scored: 24_js_machine_traces is unscored because required state labels were absent from its observations. Its answer has no effect on the score.

A canary GUID helps investigate contamination; it does not prove that training-data leakage is absent.

→

One blind attempt, graded by fuzz-tested oracles

The model gets one blind attempt at each public prompt. For Deadline 3.4, a private controller keeps the tests and expected answers outside the candidate environment. Python and JavaScript run in isolated containers that receive submitted code, public files, and invocation inputs. The controller compares returned values and exceptions; printing a success message cannot award credit. Tests include deterministic fuzzing and explicit invalid-input checks. Local development runs remain private and cannot be certified.

100

Scored out of 100, weighted by difficulty

The 26 scored tasks total 1,205 points, normalized to 100. The headline measures correctness. For valid completed answers, task credit is q2 − 0.15 × (1−q)2, where q is the matched fraction balanced equally across reviewed semantic areas within each function, then equally across functions. SQL balances empty and nonempty result classes. Duplicate inputs count once across groups. Every case must pass for full task credit.

This continuous rule replaces the old requirement to fully pass a group before receiving positive partial credit. Negative penalties remain: q=0 earns −15% task credit; q=0.5 earns 21.25%; q=1 earns 100% if every case passes. Invalid or incomplete execution receives −15%, explicit skips earn zero, and unresolved blank replies suppress the headline score.

The headline keeps the published task point values and displays two decimals. The downloadable result data includes equal-task and equal-family scores, plus ranks with each family omitted, to expose sensitivity to weighting. The nine families are cipher, state machine, codec, calendar, expression, pair counting, interpreter, SQL and repository repair; equal-family scoring weights tasks equally within each family. These comparisons are not confidence intervals.

DL Score additionally discounts positive credit by budget divided by output tokens when over budget. Measured values require complete per-task token measurements. Reconstructed estimates are marked ≈, with their assumptions and sensitivity in the result's post-mortem. Client-reported measurements and effort labels are not independently authenticated.

New certified official runs require at least three independent attempts per task. The displayed repeat standard deviation is not a confidence interval. Historical official generations may have only one attempt; regrading them does not create extra samples. Saved generations followed their original scoring instructions. A retrospective regrade evaluates those answers; it cannot show what a fresh attempt under revised scoring incentives would produce. The strict score counts only tasks fully passed on every attempt. Scores from different benchmark versions or task hashes must not be pooled.

2×

Two kinds of results

OFFICIAL identifies maintainer-run generations. Existing entries are historical single-attempt results unless labeled otherwise. A saved answer can be regraded with the new private tests, preserving its original sample count and generation provenance.

COMMUNITY answers use the existing public submission format. Only complete, isolated regrades from matching benchmark and runtime versions are aggregated. Scores measure the submitted code; model attribution, effort settings, token counts and timing remain client reported. Multiple submissions alone do not prove independence.

What Deadline measures — and what it does not

Deadline measures exact Python 3, JavaScript (Node), and SQLite SQL, standard libraries only, across 27 public tasks (26 scored in version 3.4). Most tasks show only the observed behavior of a hidden system — the model must reverse-engineer its rules — in one blind attempt, against token deadlines. Reproducing the given examples earns nothing, a half-cracked theory earns little (continuous credit is q² − 0.15(1 − q)², using balanced semantic matches). Invalid execution receives −15%; explicit skips earn zero. Two of the tasks are whole-project bug hunts across dozens of generated files. It does NOT measure dependency wrangling or long agentic sessions. A high Deadline score means correct inference under pressure; it is not a claim about all of software engineering.

What keeps it honest

Private expected answers, a separate comparison controller, typed results, bounded execution, immutable per-attempt records and content hashes support grading integrity. Duplicate and style checks are review signals, not proof of cheating or model identity. The calibration audit runs all 26 scored reference solutions, 44 deliberately broken implementations and 3 independent correct alternatives in Docker. Focused contract checks cover signed division, codec validation, scope and call depth; separate independent calculations check the private expected results. Generated tasks remain finite tests, not proof of correctness for every possible input. Universal passes limit the suite's ability to separate models. Additional decimal places do not establish meaningful differences between single attempts.

TIME-DL applies time-budget discounts to the current correctness grades using the original saved answer-file intervals. Its budgets are 60, 120, 240 and 450 seconds for medium, hard, brutal and nightmare tasks. Missing or zero intervals receive no time discount, following the original convention; this can overestimate TIME-DL. Negative credit is never discounted. Expanded model rows show the timing coverage. File intervals do not establish inference latency; TIME-DL is a descriptive estimate. Correctness determines the agent leaderboard order. API generation time is recorded separately from grading time.

  • No judge model — style earns nothing, only passing tests count.
  • No self-reported scores — every number on the site was graded here.
  • No second chances — one blind attempt per task, per sample.
