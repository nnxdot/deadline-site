How it works

Deadline is a closed coding benchmark. Models get one blind shot at original tasks, and hidden tests decide. No judge model. No vibes.

4.0

Deadline 4.0 — calibration in progress

The new suite contains 72 scored tasks across nine families, totaling 800 points. Debugging and maintenance contribute 60% of the points: repository debugging, regression finding, behavior-preserving refactoring, diagnosis and performance. Inference, exactness, specification compliance and SQL contribute 40%. Languages are Python, JavaScript, TypeScript, Go and SQLite SQL. Each family has eight tasks; baseline, hard and stress are design targets rather than proven difficulty labels.

Two separate lanes: raw API responses without tools, and agents using local tools and self-tests in fresh public task rooms. Private Docker graders check both lanes. Results from different lanes, waves or grading suites are never pooled.

Partial credit is q4 − 0.15(1 − q)2, balanced across semantic areas. All cases must pass for full credit. Invalid execution receives −15%; skips earn zero; missing or truncated replies stay incomplete.

Agent score: positive credit is multiplied by min(1, output budget / output tokens). Exceeding the total-token ceiling forfeits positive credit; negative penalties are unchanged. Every model output, including reasoning and intermediate output, counts. Total tokens include input plus output, with cached input counted once at face value. Wall time is recorded but never scored.

Output deadlines use two thirds of the lowest fully correct observed output usage, rounded up to 250 with a 1,000-token floor. Total ceilings use ten times that solve's input plus output, rounded up to 25,000 with a 100,000 floor. Limits only tighten for an unchanged task. Without a correct solve, there is no output discount and the ceiling uses forty times the public payload estimate; existing ceilings persist when a first solve arrives. Both limits must be printed before a fresh attempt. The API lane retains its separate output-token scoring regime.

Agent ranking puts a complete sweep without ceiling forfeitures first, then deadline score, then correctness. Release calibration is still incomplete. A future official entry requires one fresh full agent sample with printed limits, or three independent API samples.

Current calibration: Astra xhigh passed 72/72 tasks, with 100% correctness and a retrospective deadline score of 58.06. The last ten answers exceeded their printed 100,000-total-token ceilings and received zero deadline credit. The first 62 used older instructions. This mixed-instruction composite is published on the 4.0 leaderboard at the maintainer's request. Its calibration provenance does not change, and it is not a certified fresh run or proof that task difficulty has reduced raw correctness.

View 4.0 information and calibration. The public 4.0 runner and submission release are pending; the commands for the 3.x client do not run this new suite.

Versions 3.x: generated tasks with private grading

Every task is GENERATED by a machine, not written by a human: hidden cipher pipelines to reverse-engineer (a difficulty ladder from depth 2 to depth 10), randomized state machines, binary formats with checksums, a scrambled calendar, expression evaluators with randomized precedence tables, performance gates where the obvious solution times out, and full interpreters whose semantics are partly generated. Most tasks involve inference: no rulebook at all, only observed behavior (machine traces, raw byte encodings, example evaluations, calendar observations, a spec with redacted semantics, example databases with the exact rows a hidden SQL report must return) from which the hidden system must be reverse-engineered. Tasks span Python, JavaScript, and SQLite SQL. The rules deliberately differ from familiar conventions. The prompts are public (in this repo), but the test suites and reference solutions are private. Public benchmark answers leak into training data and inflate scores; Deadline's graders never leave the maintainer's machine.

The 27 public prompts and submission format remain unchanged. In Deadline 3.5, 24 tasks are scored; tasks 19, 22 and 24 are unscored. The version selector retains the historical 3.4 results with 26 scored tasks and only task 24 excluded.

A canary GUID helps investigate contamination; it does not prove that training-data leakage is absent.

One blind attempt, graded by fuzz-tested oracles

The model gets one blind attempt at each public prompt. For the 3.x scoring versions, a private controller keeps the tests and expected answers outside the candidate environment. Python and JavaScript run in isolated containers that receive submitted code, public files, and invocation inputs. The controller compares returned values and exceptions; printing a success message cannot award credit. Tests include deterministic fuzzing and explicit invalid-input checks. Local development runs remain private and cannot be certified.

Versioned scores out of 100

Deadline 3.5 scores 24 tasks totaling 1,050 points. Its headline discounts correctness by output tokens: positive task credit is multiplied by min(1, task budget / output tokens). Negative penalties are never discounted. Undiscounted Correctness stays visible. Missing per-task usage means no headline; the run still has a correctness result. Existing reconstructed estimates are marked ≈.

For valid completed answers, 3.5 task credit is q4 − 0.15 × (1−q)2, where q is the matched fraction balanced equally across semantic areas within each function, then across functions. SQL balances empty and nonempty result classes. Duplicate inputs count once. Every case must pass for full credit. At q=0.5, task credit is 2.5%; at q=0.9, it is 65.46%.

Tasks 19, 22 and 24 are unscored in 3.5. The first two have hidden rules that their public observations do not determine; task 24 omits required final-state labels. Invalid execution receives −15%, skips earn zero and unresolved replies remain incomplete.

Deadline 3.4 remains available through the version selector with all original results: 26 scored tasks, 1,205 points, q2 − 0.15(1−q)2 credit, correctness as the headline, and Token DL alongside it. Only task 24 is unscored in 3.4. These versions are not directly comparable. Regrading uses the same saved answers, not new model attempts.

Correctness keeps the published point values for scored tasks and displays two decimals. The downloadable result data includes equal-task and equal-family scores, plus ranks with each family omitted, to expose sensitivity to weighting. The nine families are cipher, state machine, codec, calendar, expression, pair counting, interpreter, SQL and repository repair; equal-family scoring weights tasks equally within each family. These comparisons are not confidence intervals.

Token DL (the 3.5 headline; a separate metric in 3.4) discounts positive credit by budget divided by output tokens when over budget. Measured values require complete per-task token measurements. Reconstructed estimates are marked ≈, with their assumptions and sensitivity in the result's post-mortem. Client-reported measurements and effort labels are not independently authenticated.

New certified 3.x official runs require at least three independent attempts per task. The displayed repeat standard deviation is not a confidence interval. Historical official generations may have only one attempt; regrading them does not create extra samples. Saved generations followed their original scoring instructions. A retrospective regrade evaluates those answers; it cannot show what a fresh attempt under revised scoring incentives would produce. The strict score counts only tasks fully passed on every attempt. Scores from different benchmark versions or task hashes must not be pooled.

Two kinds of results

OFFICIAL identifies maintainer-run generations. Existing entries are historical single-attempt results unless labeled otherwise. A saved answer can be regraded with the new private tests, preserving its original sample count and generation provenance.

COMMUNITY answers use the existing public submission format. Only complete, isolated regrades from matching benchmark and runtime versions are aggregated. Scores measure the submitted code; model attribution, effort settings, token counts and timing remain client reported. Multiple submissions alone do not prove independence.

What Deadline measures — and what it does not

Versions 3.x measure exact Python 3, JavaScript (Node), and SQLite SQL, standard libraries only, across 27 public tasks (24 scored in 3.5; 26 in 3.4). Most tasks show only the observed behavior of a hidden system — the model must reverse-engineer its rules — in one blind attempt, against token deadlines. Reproducing the given examples earns nothing, a half-cracked theory earns little (continuous credit uses balanced semantic matches and the selected version's partial-credit curve). Invalid execution receives −15%; explicit skips earn zero. Two of the tasks are whole-project bug hunts across dozens of generated files. It does NOT measure dependency wrangling or long agentic sessions. A high Deadline score means correct inference under pressure; it is not a claim about all of software engineering.

What keeps it honest

Private expected answers, a separate comparison controller, typed results, bounded execution, immutable per-attempt records and content hashes support grading integrity. Duplicate and style checks are review signals, not proof of cheating or model identity. The 3.5 calibration audit executes all 24 scored reference solutions, deliberately broken controls and independent correct alternatives in Docker. A separate mutation screen was reviewed against the complete public prose and examples; it does not prove general uniqueness. Focused contract checks cover signed division, codec validation, scope and call depth; separate independent calculations check the private expected results. Generated tasks remain finite tests, not proof of correctness for every possible input. Universal passes limit the suite's ability to separate models. Additional decimal places do not establish meaningful differences between single attempts.

TIME-DL applies time-budget discounts to the current correctness grades using the original saved answer-file intervals. Its budgets are 60, 120, 240 and 450 seconds for medium, hard, brutal and nightmare tasks. Missing or zero intervals receive no time discount, following the original convention; this can overestimate TIME-DL. Negative credit is never discounted. Expanded model rows show the timing coverage. File intervals do not establish inference latency; TIME-DL is a descriptive estimate. Version 3.5 ranks by the token-discounted headline; unmetered entries keep correctness without a headline rank. Version 3.4 ranks by correctness. API generation time is recorded separately from grading time.

  • No judge model — style earns nothing, only passing tests count.
  • No self-reported scores — every number on the site was graded here.
  • No second chances — one blind attempt per task, per sample.
